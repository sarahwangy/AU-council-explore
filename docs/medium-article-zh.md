# 我用 Vibe Coding 做了一个覆盖全澳洲的社区生活指南

> 从搬家焦虑到全栈落地：一个开发者用 AI 协作流程构建地图应用的实战记录

---

## 起点：一个真实的生活困境

我要搬去墨尔本。

朋友推荐 Glen Waverley，说学区好；同事说 Brunswick 更有生活气息；房产中介把 Doncaster 说得天花乱坠。我坐在电脑前，开了十几个政府网站——澳洲统计局、各州 council 官网、Google Maps、Domain——在它们之间反复切换，试图回答一个很朴素的问题：

**这些地方，到底哪个更适合我住？**

每个网站只告诉我一部分答案。人口数据在这里，托儿所在那里，活动日历又在另一个地方。没有一个平台能把它们整合起来，放在同一张地图上让我对比。

于是我决定自己做一个。

这就是 **[Australia Council Explorer](https://au-council-explore.vercel.app)** 的起点——一个覆盖全澳洲所有 council 区域的交互式生活数据平台。

---

## 这个平台能做什么？

一张覆盖全澳洲的交互式地图，点进任何一个 council，你可以看到：

- 📚 图书馆活动日历（亲子活动、工作坊、展览）
- 👶 托儿所列表，含 ACECQA 官方质量评级
- 🏥 周边医院和急诊信息
- 🛝 游乐场位置与设施筛选（围栏、遮阳、BBQ）
- 📊 人口数据：年龄分布、教育程度、语言、房价中位数
- 🏫 学区查询——输入地址，看归属哪个学区

还可以多个 council 并排对比，以及用 AI 自然语言搜索——"悉尼附近哪个区托儿所最多？"

**这是做给新移民、换城市的家庭、以及所有想认真研究"住哪"这件事的人的工具。**

## 技术栈

| 层 | 技术 |
|----|------|
| 前端框架 | Next.js 16 App Router |
| 数据库 | Prisma + Neon PostgreSQL（serverless）|
| 地图 | Mapbox GL JS |
| 样式 | Tailwind CSS v4 |
| AI 搜索 | Anthropic Claude Haiku |
| 地理编码 | Mapbox Geocoding + Nominatim（OSM）|
| 数据采集 | GitHub Actions 每日 cron |
| 部署 | Vercel |

数据来源：ABS 人口普查、ACECQA 全国托儿所数据库（6,303 条 VIC 记录）、OSM Overpass（医院、游乐场）、以及三个活动平台：mylibrary.digital、Humanitix、Eventbrite。爬虫每天凌晨 1 点自动跑，结果写入 Neon 数据库。

## 什么是 Vibe Coding？

在聊技术之前，我想先说说这次的开发方式。

"Vibe Coding"不是一个正式的工程术语，但它准确描述了我近来的工作状态：**你不是在单打独斗地写代码，而是和 AI 共同驾驶整个开发过程**。你负责判断方向、审查决策、把控质量；AI 负责草稿、模板、细节、调试建议。

工具是 Claude Code，搭配一套叫 **Superpowers** 的方法论。它把开发流程拆成几个阶段，每个阶段都有对应的 skill：

### 头脑风暴：先想清楚，再动手

Liveability Score 的权重怎么定？这是一个设计问题，不是数学问题。在动手写代码之前，我用 Brainstorming skill 和 Claude 讨论了一轮。

对话里 Claude 提出了几个我没想到的角度：托儿所和医院的重要性对不同人群差异很大；分数是绝对值还是相对于全州均值？透明度比精确度更重要吗？

这一轮对话的产出不只是公式本身——更重要的是做了一个决定：分数要透明，每个 suburb 页面展示每一类设施的得分细节，不只是一个总分。用户应该能验证他们看到的数字从哪来。

最终的公式：托儿所 × 30% + 医院 × 30% + 图书馆 × 20% + 游乐场 × 20%。

### 写计划：文件路径比代码先到

每个功能动手之前，我先用 Writing Plans skill 生成一份实现计划——哪些文件要创建、每个文件的职责、接口定义。

这个习惯省掉了大量的"写到一半发现结构不对"的返工。计划做好之后，写代码变成了按图施工，而不是边走边想。

### 独立 sub-agent：每个爬虫一个 agent

数据管道有五个独立的爬虫：ACECQA 托儿所、OSM 医院、OSM 游乐场、三个活动平台。它们的 API 不同、数据结构不同、失败方式也不同。

我用 Subagent-Driven Development skill，让每个爬虫由一个专属的 sub-agent 独立实现，各自有独立的上下文窗口。好处立刻体现：Humanitix 爬虫出了 400 错误，我在隔离环境里调试，完全不影响其他爬虫。

### 系统性调试：先找根因，再动手修

这周最难追的 Bug：点击右侧列表里的医院，地图闪了一下，flyTo 没有触发，popup 没有出现。

系统性调试从一个问题开始：*出问题之前，什么改变了？*答案是 `selectedId`。顺着这条线往下追，发现根因不在 fly-to 逻辑里——是上游一个没有 memoize 的数组，每次渲染都产生新引用，触发了地图实例重建，popup 引用表被清空，flyTo 找不到目标。

二十分钟找到根因。如果没有系统性的追踪方式，可能花一个小时看错误的地方。

### 完成前验证：真实流程跑一遍

全国搜索功能做完之前，我用 Verification skill 跑了几个真实的用户流：搜索"Parramatta"，确认地图从 VIC 切换到 NSW 并飞到正确边界；用慢网络测试，确认不会静默超时。

提前发现了两个问题——都在上线前修好了。

## 数据管道：把散落的公开数据拼起来

ACECQA 全国托儿所注册库是一个很了不起的公共资源——6,303 条维州服务记录，含质量评级、营业时间、地址，全部公开。把它导入数据库需要处理几个细节：CSV 字段里有含逗号的引用字符串（标准 split 会挂），地址需要 Geocoding 转坐标（5,091 条成功），以及幂等的 upsert 逻辑让脚本可以安全重跑。

游乐场数据来自 OSM：6,054 个游乐场，但 86% 没有名字。这不是问题——每个地点都有坐标，坐标可以用 Nominatim 反向地理编码成人类可读的名字，一个隔夜批处理任务搞定。脚本每次只查 `name IS NULL` 的记录，可以随时中断重启。最终：6,054 个游乐场中 5,929 个命名成功（97.9%）。

这是我在这个项目里反复体验到的事：**政府公开数据其实很丰富，缺的是整合**。

## Liveability Score：让数字有意义

早期版本的 council 详情页直接展示原始数量：14 个托儿所、2 家医院、8 个游乐场。用户看着这些数字不知道怎么判断。

Liveability Score 把四个维度折叠成一个 0–100 的数字，配上颜色（红/橙/绿）。数字本身告诉你状态，颜色告诉你直觉方向，对比页回答"跟谁比"。

分数在请求时实时计算，不存数据库——爬虫数据更新后分数自动随之变化。基准值是全澳洲所有 council 的中位密度，100 分代表中位，不代表满分。这让不同城市之间的比较有意义，而不是一个绝对的高低判断。

## 全局搜索：让工具感觉不一样

首页搜索最初只能搜 VIC 的 council。全国化之后：输入任意 council 名，回车，地图自动切换到对应的州，精准飞到那个 council 的边界。

技术改动大概四个小时。但工具的感觉变了——从"一个维州地图应用，附带其他州"变成"一个覆盖全澳洲的工具"。**第一方搜索体验对产品定位的影响远超技术工作量。**

一个实现细节值得提：原版用固定 900ms 等待 GeoJSON 加载，慢网络下完全不够，快网络下又浪费。改成每 100ms 轮询一次（最多等 4 秒），数据好了就飞，没好就等。这是异步等待的通用原则：轮询比固定 sleep 可靠得多。

## AI 协作的感受

这是我第一次在一个有一定规模的项目里全程用 Vibe Coding 工作。几个真实的感受：

**AI 最擅长的**：把模糊问题转化成具体实现计划；调试时帮你梳理依赖链和执行流；生成样板代码让你有东西可以审查和改。

**AI 不能替代你的**：判断这个功能值不值得做；评估 trade-off（Liveability Score 的权重选择本质上是价值判断）；确保生成的代码真正符合项目上下文。

我保持的原则是：**AI 写草稿，我来评审**。每一段 agent 生成的代码在合并前我都亲自读过。不是不信任 AI，而是我需要真正理解自己的代码库。

## 这是 MVP 1

应用能用，已上线，解决了当初的问题。但这是起点，不是终点。

下一步：Brisbane、Sydney、Adelaide、Perth 的 council 数据接入；更丰富的 suburb 人口细节；AI 自然语言搜索（"悉尼附近哪个区托儿所最多？"）；活动邮件订阅；多语言支持（中文、越南语）。爬虫基础设施已经搭好——大多数剩余 council 只需要加配置，不需要写新爬虫。

我会持续维护这个项目，因为它解决的问题是真实存在的，而且会一直存在。

如果你有一个痛点，一个现有产品回答不了的问题，一份你希望有人整合的数据——不妨试着做出来。用 AI 作为你的协作伙伴。你不需要成为专家，你只需要一个清晰的问题和愿意不断迭代的耐心。
